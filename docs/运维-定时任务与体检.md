# 运维：定时采集与数据体检

## 一、定时采集（已配置）

| 项 | 值 |
|---|---|
| 任务名 | `pricewatch-collect` |
| 计划 | 每 **30 分钟** 一次，立即生效、无限期重复 |
| 执行 | `cmd /c "D:\dsh work\比价\run-collect.cmd"` |
| 日志 | `logs\collect.log`（每轮写入 start/done 时间戳）|
| 状态 | 已启用（`Status: Ready`）|

**一轮做什么**：显卡 12 + 内存 11 + 电源 5 + 机箱 5 + 键盘 5 + 路由器 4 + 投影仪 4
→ `quality.mjs` 重算 active → `export.mjs` 重新生成快照。实测**约 1.5 分钟一轮**。

### 常用命令

```powershell
schtasks /query  /tn "pricewatch-collect" /v /fo LIST   # 看下次运行时间
schtasks /run    /tn "pricewatch-collect"               # 立刻跑一次
schtasks /change /tn "pricewatch-collect" /disable      # 暂停
schtasks /change /tn "pricewatch-collect" /enable       # 恢复
schtasks /delete /tn "pricewatch-collect" /f            # 删除
Get-Content "D:\dsh work\比价\logs\collect.log" -Tail 20 # 看日志
```

> 演示当天建议：**放演示前先 `/disable`**，避免采集和演示抢资源；演示完再 `/enable`。

## 二、数据体检 `src/check.mjs`

演示前 10 秒跑一次，输出 `PASS` / `FAIL`：

```powershell
cd "D:\dsh work\比价"
D:\nodejs\node.exe src\check.mjs
```

它检查 7 类问题：

| # | 检查 | 判定 |
|---|---|---|
| 1 | 品牌缺失比例 | >30% 警告 |
| 2 | 价格越界（<100 元 / >10 万元）| 出现即 FAIL |
| 3 | 历史点分布（min/中位/max）| <2 点的商品给警告 |
| 4 | 最近一轮抓取 | 被中止 / 全失败 警告或 FAIL |
| 5 | 重复记录（product+platform+captured_at）| 出现即 FAIL |
| 6 | 快照与库是否一致、图片是否齐全、msrp 量级 | 不一致/缺失 警告 |
| 7 | 第三方参考行数 | 没有则警告 |

退出码：`0` = PASS，`1` = FAIL（可接进 CI 或演示前脚本）。

## 三、体检发现问题时怎么办

| 症状 | 处理 |
|---|---|
| 某品类 0 个在售 | 多半是 ZOL 列表页没当代型号（CPU 就是这样），或解析规则变了 |
| 价格越界 | 看 `data/raw/zol/` 里对应快照，改 `parsePriceCents` |
| 快照与库不一致 | 忘了跑 `export.mjs` |
| 品牌缺失高 | 补 `src/zol.mjs` 的 `BRANDS`，再跑 `src/rebrand.mjs` |
| 历史点太少 | 等定时任务跑几轮；或手动 `schtasks /run` |

## 四、2026-10-19 更新：加深每轮深度

**问题**：原来每品类只抓 5~12 个，品类内有货但没进库。

**调整**（同时把频率从 30 分钟改成 60 分钟，保持每小时请求量不变）：

| 品类 | 每轮条数 | 在售 |
|---|---|---|
| 显卡 | 22（仅当代型号）| 11 |
| 内存 | 20 | 20 |
| 电源 | 16 | 19 |
| 机箱 | 16 | 19 |
| 键盘 | 16 | 19 |
| 路由器 | 12 | 12 |
| 投影仪 | 12 | 14 |
| 笔记本 | 8 | 7 |
| **合计** | **约 122 请求/轮** | **121** |

- 一轮耗时约 **5~6 分钟**
- 计划任务改为 **每 60 分钟**（`schtasks /query /tn pricewatch-collect` 可查）
- 新一轮会同时跑 `images.mjs`，补新商品的本地图

**为什么改频率**：请求数翻倍到 122 次/轮，若仍 30 分钟一次，每小时 244 次请求会明显触发 ZOL 限速（实测已有 aborted 轮次）。

## 五、2026-10-19 晚：京东映射批次（随机间隔）

负责人要求"慢慢跑"，并让间隔随机，降低被风控的概率。

| 项 | 值 |
|---|---|
| 任务名 | `pricewatch-match` |
| 频率 | **每 40 分钟**一批 |
| 每批数量 | 6 个商品 |
| **间隔** | **每处理一个商品，随机等 90~180 秒**（`--gap-min 90000 --gap-max 180000`）|
| 防重入 | `data/.jd-match.lock`，锁在 35 分钟内则跳过 |
| 熔断 | 撞到京东"PC频控页"→ 写 `data/.jd-cooldown.json`，**60 分钟内所有京东请求自动跳过** |
| 熔断期间表现 | `/api/jd-price` 返回 `reason:"jd_cooldown"` + 上次价格 |
| 断电/关机 | 计划任务在下次开机/唤醒后自动继续；冷却按时间戳判断，不受影响 |

### 吞吐估算

- 一批 6 个 ≈ 12~20 分钟（随机间隔）
- 每 40 分钟一批 → **约 9~12 个/小时**
- 剩余 ~113 个 → **约 10~12 小时的实际通电时间**

### 想加快时

```powershell
# 白天插电时：每批 10 个、间隔 60~120 秒
& D:\nodejs\node.exe src\jd_match.mjs --limit 10 --gap-min 60000 --gap-max 120000
```

撞到频控就停，别硬顶——历史上冷却 60 分钟起步。
