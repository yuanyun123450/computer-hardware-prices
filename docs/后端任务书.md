# 后端任务书（数据侧 → 后端）

> 配套：`src/serve.mjs`（**已能跑的参考实现，可以直接搬，也可以重写，只要接口契约不变**）
> 数据源：`data/price.db`（SQLite）+ `data/snapshot.json`（导出快照）

---

## 一、接口清单（共 9 个，不是 7 个）

| 方法 | 路径 | 说明 | 状态 |
|---|---|---|---|
| GET | `/api/snapshot` | 返回快照，`{ok, data, error}`，`data` 结构 = `snapshot.json` | ✅ |
| GET | `/api/health` | `{db, data_at, exported_at, last_collect_at, collecting}`（`db` 是真探活：`SELECT 1`）| ✅ |
| POST | `/api/refresh` | 触发一轮采集（collect → quality → export），立刻返回 | ✅ |
| GET | `/api/collect/status` | `{collecting, last_refresh:{exits,data_changed,...}, runs}` | ✅ |
| GET | `/api/search?q=` | 模糊搜索 Top5；`score` 是 **0–100 整数** | ✅ |
| POST | `/api/alias` | 记住用户选择（`product_id:null` = 标记“都不对”）| ✅ |
| POST | `/api/quote` | 券后价计算（**核心卖点**）| ✅ |
| GET/POST | `/api/user-coupons` | 扩展上报/读取用户券（内存，TTL 10 分钟）| ✅ |
| GET | `/api/images/<file>` | 本地图（映射 `data/images/`，只允许 basename）| ✅ |

统一外层：

```json
{"ok":true,"data":{...},"error":null,"generated_at":"2026-10-18T21:08:49+08:00"}
```
失败：`{"ok":false,"data":null,"error":{"code":"BAD_REQUEST","message":"..."}}`

**错误码枚举（7 个，全项目统一这份）**：

| code | 何时用 |
|---|---|
| `NOT_READY` | 还没有数据（快照不存在）|
| `RATE_LIMITED` | 刷新过频（也可用 `refreshed:false + retry_after` 表达）|
| `NOT_AVAILABLE` | 本机缺脚本/缺能力，做不了这件事 |
| `NOT_IMPLEMENTED` | 接口存在但没实现 |
| `BAD_REQUEST` | 参数非法（缺字段、越界、指向不存在的商品）|
| `FORBIDDEN` | 跨域来源不在白名单 |
| `NOT_FOUND` | 资源不存在（如图片） |

> 历史文档里出现过 `SOURCE_DOWN`，**已废弃**，不要再用。

## 二、刷新接口的三条硬规则

1. 全站最小间隔 **60 秒**（`lastRun` 落库或至少在进程内，重启丢可以接受但要写注释）
2. 同一时刻只允许一轮（`collecting` 标记）
3. **必须如实报告结果**：采集/导出跑完后写 `last_refresh = {data_changed, data_at_before, data_at_after}`
   - `data_changed` 的判定：比较 `snapshot.generated_at`（= 数据时间）前后是否变化
   - **不要**用导出时间判断，否则会出现“6 秒后时间变了但价格没变”的假刷新（前端已实测过这个坑）

另外：采集脚本的 stdout/stderr **必须落文件**（`logs/collect-*.log`），不要 `stdio:"ignore"`——失败时没证据。

## 三、`/api/search` 的算法（这部分数据侧负责，你负责接）

数据侧会提供 `src/match.mjs`，导出：

```js
// 返回 [{product_id, title, brand, price, image_url, score, why:[...]}]
matchCandidates(query, products, { limit = 5 })
```

打分维度（**硬门槛 + 加权**，不是纯相似度）：

| 规则 | 处理 |
|---|---|
| 品牌不符 | 直接淘汰（搜“华为”不出“荣耀”）|
| 型号数字缺失 | 淘汰（`4070` ≠ `4070S` ≠ `4070 Ti`，后缀单列）|
| 容量不符（12GB vs 16GB）| 淘汰 |
| 多品牌堆词 / 多型号杂糅 | 淘汰（店铺通用标题）|
| 词覆盖度 / 系列词命中 | 加分，产出 `score` 与 `why` |

你只需要：

```js
const { matchCandidates } = await import('./match.mjs');
const data = matchCandidates(q, readSnapshot().products, { limit: 5 });
```

## 四、`POST /api/alias` 与别名表

```sql
CREATE TABLE IF NOT EXISTS product_alias (
  id         INTEGER PRIMARY KEY,
  raw_title  TEXT NOT NULL UNIQUE,
  product_id INTEGER,              -- NULL = 用户说"都不对"
  source     TEXT NOT NULL,        -- user_pick / user_reject
  created_at TEXT NOT NULL
);
```
- 幂等：同 `raw_title` 再提交就 `ON CONFLICT DO UPDATE`
- 搜索时**先查别名表**：命中就直接返回那一条（`source: "alias"`），没命中再走 `matchCandidates`

## 五、数据库使用注意

```sql
PRAGMA journal_mode=WAL;      -- 已经开了，别关
PRAGMA busy_timeout=5000;
PRAGMA query_only=ON;         -- 接口进程只读，写只发生在采集进程
```

- 采集器一个事务写完整轮，不要每条 commit
- **派生数据不要落库**：`is_good_deal`、`market_min`、`discount_vs_msrp` 都在 `export.mjs` 里算，库里没有这些列
- 价格单位全库统一「分」

1. 不在请求里同步跑采集（会超时）——必须 spawn 后立刻返回

## 八、券后价（用户券）v1 规格 —— 本项目主打卖点

### 8.1 背景与边界（先读）

- 个人券不可代表他人，**不进主数据、不做“全网最低”排名**
- 但“**你自己**的券后价”是真实且可解释的卖点，单独一条链路
- 券只在**用户自己的浏览器里**读取（浏览器扩展），**不写库、不打日志、不进快照**

### 8.2 链路

```
用户在自己京东页登录
  → 我们的浏览器扩展（content script，注入 item.jd.com）
  → 读到该商品页公开+个人可见的券（面额/门槛）→ 归一化成 [{threshold, amount, stackable}]
  → POST 本机 http://127.0.0.1:8787/api/user-coupons  {sku, coupons[]}   （只存活在内存，TTL 10 分钟）
  → 我们的前端页面 GET /api/user-coupons?sku=xxx 拿到券
  → 前端把「价格 + 券」交给 POST /api/quote 算出三档价
```

### 8.3 接口 1：券后价计算（核心，必修）

```
POST /api/quote
{
  "price": 338837,                 // 分
  "auto_promo": 1000,              // 平台自动立减（可空）
  "user_coupons": [                // 用户券，可空数组
    {"threshold": 500000, "amount": 30000, "stackable": false},
    {"threshold": 0,      "amount": 5000,  "stackable": true}
  ]
}
→ 200
{"ok":true,"data":{
  "price": 338837,                 // 页面价
  "price_promo": 337837,           // 减掉自动立减 10 元
  "price_user": 332837,            // 再用一张“无门槛减50”
  "final": 332837,
  "applied": [{"amount":5000,"threshold":0,"stackable":true,"reason":"可叠加"}],
  "notes": ["再买 ￥1611.63 可用「满5000减300」"]
},"error":null}
```

> ⚠️ 上面这个示例是**修过的**：早期版本里把 `threshold=500000` 的券放进了 `applied`，
> 与规则 1 自相矛盾（3388.37 < 5000，本该进 `notes`）。以规则为准，别抄旧示例。

**计算规则（照抄，别自由发挥）**：

1. 只有 `threshold <= price` 的券可用；不满足的进 `notes`
2. `stackable=false` 的券之间互斥 → **取单张最优**
3. `stackable=true` 的券可叠加在最优的那张之上
4. `final` 不能小于 0
5. 所有金额单位 **分**，四舍五入用整数运算
6. 支付优惠（白条/银行卡）**不参与**，只做提示

### 8.4 接口 2：扩展回传券（内存，不落库）

```
POST /api/user-coupons   {"sku":"100378244340","coupons":[{...}]}
→ {"ok":true,"data":{"stored":2,"ttl_seconds":600}}
GET  /api/user-coupons?sku=100378244340
→ {"ok":true,"data":{"coupons":[...],"received_at":"..."}}
```

要求：
- 只存内存 `Map`，**TTL 10 分钟**自动过期
- 同一 `sku` 重复上报就覆盖
- `POST` 时**先校验后判断**：`amount` 必须 ≤ `500000` 分、`threshold` ≤ `10000000` 分；
  **任何一张越界 → 整批拒绝**，返回 `ok:false / BAD_REQUEST` + `data.rejected` 列表（不要 `filter` 静默丢弃）
- **不写数据库、不写日志内容**（日志只记条数）
- CORS：只允许 `http://localhost[:port]`、`http://127.0.0.1[:port]` 与浏览器扩展来源；其它来源返回 `403 FORBIDDEN`

### 8.5 扩展的边界

- 只在 `item.jd.com` 注入，只读页面 DOM，**不读 cookie、不改页面**
- 用户主动点“同步我的券”才发请求；不发就不发
- 扩展代码走 `frontend` 同学或数据侧给的骨架（见 `src/extension/`），后端只对接上述两个接口

### 8.6 验收用例（6 条）

1. 无券 → `final === price_promo`
2. 一张 `满5000减300` 且 price=338837 → 不满足，`notes` 含“再买 ￥X”
3. 一张无门槛 `减50` → `final = price_promo - 5000`
4. 两张互斥券（减300 / 减200）→ 选减300
5. 一张互斥减300 + 一张可叠加减50 → `final = price_promo - 350`
6. 券额大于价格 → `final = 0`，不能为负

## 十、2026-10-19 契约修订（验收后补，以本节为准）

| # | 项 | 修订后 |
|---|---|---|
| 1 | 刷新链路 | **三步**：`collect.mjs → quality.mjs → export.mjs`，`last_refresh.exits` 记录三步退出码；任一步 `timeout` 也要复位 `collecting` |
| 2 | 静态服务 | **只放行白名单**：`/`、`/web/*`、`/data/images/*`、`/data/snapshot.json`、`/data/bili/export.json`、`/data/bili/reports.csv`。`price.db`、源码、`logs/`、`data/raw/`、`browser-profile/` 全部 404 |
| 3 | 图片 | `GET /api/images/<file>` 只接 basename，越界 404；后端包**必须**带 `data/images/` |
| 4 | 冷却 | 允许**进程内**实现（重启丢失可接受）；任务书与手册统一按这条，不再要求落库 |
| 5 | `price_flag` | 该字段非空时，`market_min` 必须为 `null`，且 `is_good_deal=false` |
| 6 | 别名 "都不对" | `product_id:null` 会写 `source=user_reject`；搜索命中时返回 `{candidates:[], source:"alias_reject"}`，**不要再回退到规则候选** |
| 7 | 别名合法性 | `product_id` 必须存在于当前快照，否则 `BAD_REQUEST` |
| 8 | `quote` 负值 | `auto_promo` 负数按 0 处理；`price` 非数字或负数 → `BAD_REQUEST` |
| 9 | 搜索 `score` | **0–100 整数**（不是 0~1），前端展示时不要再乘 100 |
| 10 | 子进程 | 必须监听 `error`、设超时（默认 5 分钟/步）、`finally` 关闭日志 fd，避免 `collecting` 永久卡死与 fd 泄漏 |
| 11 | 接口文件名 | 统一 `src/serve.mjs`（手册里旧写的 `src/server.mjs` 已废弃）|
| 12 | 刷新范围 | 用户点刷新只采**显卡**（约 40 秒）；全量 8 品类由定时任务负责（约 4 分钟），这是有意的取舍 |

## 十一、券口径（最终，覆盖前面所有说法）

1. **数据侧只入库"页面自动立减"**：`source='public_auto'`、`is_public=1`、`need_action='auto'`
2. **满减/领券类、PLUS/新人/百亿/定向/专享/学生/白条 一律不入库**（无法证明人人可领）
3. **券后价只能由用户自己的券算**：`/api/user-coupons`（内存 TTL 10 分钟）→ `/api/quote`
4. **服务端绝不持久化券**，也不把抓取账号的券写进任何表
5. `snapshot` / `deal` 里**没有**"券后价"字段——它是运行时结果，不是数据
6. `src/check.mjs` 第 8 节是这条口径的自动守卫，FAIL 就不许发版

## 十二、映射接口 `/api/jd-match`（2026-10-19 新增）

### 12.1 查询

```
GET /api/jd-match?status=review&limit=50
→ {"ok":true,"data":{
     "counts":{"review":12,"matched":5,"none":30},
     "items":[{"product_id":8,"model":"索泰RTX4070","jd_sku":null,"status":"review",
               "score":65,"official":1,
               "candidates":[{"sku":"100...","name":"...","price":529900,"official":true,"score":65}]}]
   }}
```

### 12.2 确认（人工点选）

```
POST /api/jd-match   {"product_id":8,"jd_sku":"100012345678"}
→ {"ok":true,"data":{"product_id":8,"jd_sku":"...","status":"matched"}}
```
要求：
- `jd_sku` 必须是 6 位以上数字；`product_id` 必须存在于当前快照，否则 `BAD_REQUEST`
- 写入 `jd_match.status='matched'` **并同步 `product.jd_sku`**
- 幂等：重复确认同一商品直接覆盖

### 12.3 约束

- `counts` 的三个桶固定为 `matched / review / none`
- `candidates` 最多 3 条，字段固定 `sku/name/price/official/score`
- 该接口**不触发采集**，只读写映射
