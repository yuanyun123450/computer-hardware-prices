# 协作：三台电脑并行建立「商品 ↔ 京东 SKU」映射

---

## 0. 你这台机器需要准备什么

| # | 需要 | 怎么来 |
|---|---|---|
| 1 | **交付-后端-v2.zip** | 由 A（数据侧）发给你；解压到任意目录，例如 `D:\pwatch\` |
| 2 | **Node ≥ 22.5** | 命令行跑 `node -v` 确认；没有就用你 DSH 自带的 node |
| 3 | 一个**带调试端口的浏览器** | 见 §0.1，用 Edge 自带命令即可，不用装任何东西 |
| 4 | **京东登录** | 在那个浏览器窗口里扫码，能进 home.jd.com 就行 |
| 5 | 你的分片号 | A 会告诉你：B 是 `1/3`，C 是 `2/3` |

### 0.1 起浏览器（不需要装插件或技能）

先关掉其它用同一 profile 的浏览器窗口，然后执行（Edge 路径按你机器实际位置改）：

```powershell
& "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" `
  --remote-debugging-port=9222 `
  --user-data-dir="$env:TEMP\pwatch-profile" `
  https://www.jd.com/
```

- 这个窗口**保持开着**，脚本靠 9222 端口控制它
- 第一次会让你登录京东，扫码即可
- 用的是**独立 profile 目录**（临时目录），不影响你平时用的浏览器

### 0.2 解压后先自检

```powershell
cd D:\pwatch\交付-后端-v2           # 换成你解压出来的目录
node src\jd_plan.mjs --shard 1/3    # B 用 1/3，C 用 2/3
```

必须看到这一行：

```
自检: 各片互不重叠=true  并集=80/80  总数一致=true
```

看不到就先别往下跑，回头找 A。

> 总指挥分配方案。目标：**不重复找 SKU、不互相覆盖、三台机器各自独立绕开京东限流**。

## 一、分工原则

| 原则 | 做法 |
|---|---|
| 不重复 | 按 `product_id % 3` 取模分片，**数学上互不重叠** |
| 可自检 | 每台机器先跑 `jd_plan.mjs --shard i/3`，它会打印"各片互不重叠 / 并集=80" |
| 可合并 | 各自导出 JSON，由 A 机器 `jd_merge.mjs` 合回；型号不一致/冲突只报告不覆盖 |
| 不重复绑定 | 合并后跑 `jd_dedupe.mjs`：**一个京东 SKU 只能属于一个商品** |

---

## 二、三台机器的分配

| 机器 | 分片 | 分到商品 | 导出文件名 |
|---|---|---|---|
| **A（我这边）** | `--shard 0/3` | 26 个 | `jd-from-A.json` |
| **B** | `--shard 1/3` | 27 个 | `jd-from-B.json` |
| **C** | `--shard 2/3` | 27 个 | `jd-from-C.json` |

> 分片是按 `product_id % 3` 算的，**不是按品类**；所以每台都同时有显卡/内存/电源等，正好均衡。

---

## 三、每台机器各自怎么做

### 共同前提

1. 解压 **`交付-后端-v2.zip`**（商品清单必须是这 80 个，否则 `product_id` 对不上）
2. 起一个带调试端口的浏览器并**登录京东**（未登录搜索会跳登录页）
3. 不要手动改数据库；所有写入都通过脚本

### 自检分片（先做，确认分到哪些）

```powershell
node src\jd_plan.mjs --shard 1/3      # B 机器改成 1/3；C 用 2/3
```
输出会包含：
```
自检: 各片互不重叠=true  并集=80/80  总数一致=true
本机执行命令：
  node src/jd_match.mjs --shard 1/3 --limit 6 --gap-min 90000 --gap-max 180000
  node src/jd_export.mjs --out data/share/jd-from-B.json
```

### 正式跑（随机间隔，撞频控自动熔断）

```powershell
node src\jd_match.mjs --shard 1/3 --limit 6 --gap-min 90000 --gap-max 180000
```

- 每个商品之间**随机等 90~180 秒**
- 撞到"PC频控页"→ 自动写冷却文件，**60 分钟内不再请求**；到点重跑同一条命令即可
- 已完成的不会重做（`jd_match` 表里有记录就跳过）

### 导出并回传

```powershell
node src\jd_export.mjs --out data\share\jd-from-B.json
```
把文件发回给 A。

## 四、A（我这边）的汇总流程

```powershell
# 1) 自己那一片
node src\jd_match.mjs --shard 0/3 --limit 6 --gap-min 90000 --gap-max 180000 --
# 2) 合并 B、C 的产出（先 dry-run 看影响）
node src\jd_merge.mjs data\share\jd-from-B.json --dry
node src\jd_merge.mjs data\share\jd-from-B.json
node src\jd_merge.mjs data\share\jd-from-C.json

# 3) 去重（一个 SKU 只能属于一个商品）
node src\jd_dedupe.mjs

# 4) 重算并导出，前端才看得到
node src\quality.mjs
node src\export.mjs
```

顺序不能反：**合并 → 去重 → 导出**。

## 五、三道防重复（已实装）

| 层级 | 机制 | 失败时表现 |
|---|---|---|
| 1. 分片 | `product_id % 3`，数学上不重叠 | `jd_plan` 自检会报 `各片互不重叠=false` |
| 2. 合并 | 型号必须一致；已 matched 且 SKU 不同 → **不覆盖**，进冲突列表 | `jd_merge` 打印冲突明细 |
| 3. 去重 | 一个 `jd_sku` 只能绑定一个商品；广告位 SKU 强制清空 | `jd_dedupe` 打印"保留 #x，降级 #y,#z" |

> 之前已经踩过一次坑：7 个不同商品都指向同一个广告位 SKU（`100007186412`），
> 以及两个 SKU 各被 2~3 个商品占用。`jd_dedupe.mjs` 就是为这类问题写的，**每次合并后必跑**。

## 六、效率与时间

| 台数 | 每批 | 随机间隔 | 每小时完成 | 80 个所需 |
|---|---|---|---|---|
| 1 台 | 6 | 90~180s | 9~12 | 7~9 小时 |
| 2 台 | 6 | 90~180s | 18~24 | 4~5 小时 |
| **3 台** | 6 | 90~180s | **27~36** | **2.5~3 小时** |

## 七、注意事项

1. **各台机器的冷却状态独立**（各自 `data/.jd-cooldown.json`），互不影响
2. **都要登录京东**：映射要读搜索结果，未登录会被跳转
3. **不要用同一个号高频**：限流看 IP，但账号行为也会被记录
4. 合并只增不减：不会删你已有的映射，只会补空缺/更新 review
5. 合并后一定要 `jd_dedupe` + `export`，否则前端看到的还是旧的
